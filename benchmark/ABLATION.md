# Ablation — full-stuffing vs two-stage prompting

Generated by `scripts/run_ablation.py`. Both arms answer the same 24 questions and share the same policy, compiler and verifier; the prompting strategy is the only variable.

The single-stage column is **not re-run** — it is read from the published `sweep-groq-r1` records, so these are the same numbers `RESULTS.md` reports.

## Bottom line

**On this subset, after one prompt fix, two-stage matches full-stuffing: same paired discrimination (3/3), no question answered worse, zero errors.** The dry run projects two-stage at ~30% fewer tokens, so on these 24 questions the saving looks free.

Three reasons not to read that as a recommendation to switch:

1. **The one row where two-stage looks *better* is an artefact.** Its 24/24 refusal score includes `t2-05`, where it answered a question that single-stage correctly flagged as ambiguous. Read the Diagnosis section before quoting that row — on the project's own terms, single-stage is right there and the scorer is wrong.
2. **It took a fix to get here.** Iteration 1 lost three questions and a paired item to a single missing sentence about time grain. Two-stage starts with less information in front of the model, so it is more sensitive to prompt defects — which is a real cost, just not one visible in a token count.
3. **24 questions cannot detect a small difference.** The full set is 80.

## Subset

24 questions, stratified by tier. Every paired-discrimination item is force-included even where that skews tier proportions away from 6/6/6/6. Those pairs are the only reflex-immune metric in the suite -- each half looks like the other and requires the opposite response -- so an ablation blind to them loses its most interesting comparison. The skew is recorded here rather than hidden: read per-tier ablation numbers as covering these questions, not a uniform sample of the tier.

## Iteration 2 — what the fix changed

Iteration 1 (`ablation-twostage`) lost three questions because the stage-A prompt never said that time grain is separate from breakdown dimensions. Stage A's schema has no `time_grain` field at all, so the only place `month` could live, from its point of view, was `valid_dimensions` — and it correctly concluded it could not express the question. Single-stage never had this problem because `QueryIntent.time_grain` is right there in its schema.

The fix is one rule added to `STAGE_A_INSTRUCTIONS`: *"breaks down by" lists non-time dimensions only; reporting by day/week/month/quarter/year is a time grain, it is set in step 2, and it is available for every metric.* Nothing else changed — same subset, same policy, same compiler, same gold.

**Questions the fix recovered: 3** — `t2-01`, `t2-04`, `t3-02`.

**Questions it newly broke: 0**.

Both counts are reported because a prompt edit that fixes three questions and breaks two is not an improvement, and only the second number would reveal it.

## Diagnosis — the defect iteration 1 found

In iteration 1 two-stage lost three questions (`t2-01`, `t2-04`, `t3-02`) for one shared reason, visible in the clarifying questions it asked:

> *"...or would you like a total net revenue for each month using a custom time grouping?"* (`t2-01`)

> *"Would you like the total reported revenue for each quarter (time aggregation) **even though quarter is not a listed breakdown dimension**?"* (`t3-02`)

All three name a time grain — month, month, quarter. The stage-A short card ends with `breaks down by: <valid_dimensions>`, and **time grain is not a dimension** in this semantic layer; it is a separate field on the intent. The full prompt says so across 28 lines; the stage-A prompt mentions grain only incidentally inside two metric descriptions. So stage A looks for "month" among the breakdown dimensions, does not find it, and correctly concludes it has been asked for something it cannot see how to express.

**That is a defect in this repo's stage-A prompt, not a property of two-stage prompting.** The ablation measured my implementation. Stated plainly because the honest conclusion from iteration 1 is *not* "splitting the prompt costs accuracy" — it is "splitting the prompt costs accuracy if you drop information the model needs, and I dropped some".

**The one question two-stage won should not be counted as a win.** On `t2-05` single-stage asked whether *"net revenue in São Paulo state"* meant `customer_state` or `seller_state`, and two-stage answered. [`docs/03-failures.md`](../docs/03-failures.md) §C1 records that question as a case where the clarifying question is *better than my gold* — both dimensions exist and the question does not say which. So two-stage scores a point here for failing to notice a real ambiguity, and the `refusal correct` row above is flattering it by one.

## What this does and does not establish

The subset is 24 questions, so a one-question change moves any rate here by 4.2 percentage points. Treat the agreement count as the finding and the per-measure rates as supporting detail; neither is powered to detect a small difference.

The paired-discrimination row is the exception worth taking seriously even at this sample size, because it is the one measure a hedging reflex cannot game. `t3-02` and `t3-03` use the same metric and differ only in whether the 2018-01-01 restatement falls inside the window, so getting one and missing the other is exactly the confusion the pair exists to detect.

Token cost is not re-measured here. `scripts/dry_run.py` projects the saving offline from the real prompts, and that projection is the cost side of this trade-off; this document is only the accuracy side.
