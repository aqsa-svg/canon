# Variance across independent runs

Generated by `scripts/write_variance.py`. Every figure in [`RESULTS.md`](RESULTS.md) is a single sample; this measures how much of that is luck.

**Why per-question flips rather than aggregate spread.** Two runs can produce an identical execution accuracy while disagreeing about *which* questions they got right, and a report showing only the aggregate would call that perfect stability. The headline here is the count of questions whose outcome changed.

## Summary

| Arm | questions | samples | flipped |
|---|---|---|---|
| `canon` | 24 | 2 | **1** |
| `baseline` | 80 | 2 | **4** |

**Arms are not pooled and the rates are not combined**, because they cover different question sets — compare the `questions` column before comparing the `flipped` column. A single blended 'variance of the benchmark' would be a number with no denominator.

## `canon` — 2 samples over 24 questions

From `benchmark/runs/variance-groq-r2/`. Same provider, same config hash, temperature 0.

**Coverage: the 24-question stratified subset**, which force-includes every paired-discrimination item and so over-represents the questions where a flip is most plausible. A *sensitive* probe, not a representative one — a clean result here is the easier half of the claim.

### Did anything change?

**1 of 24 questions changed outcome between runs.**

| Question | run 0 | run 1 |
|---|---|---|
| `t2-05` | asked, value=None | answered, value=True |

A flip at temperature 0 is not a contradiction: the provider does not guarantee determinism. Each one above is a question whose published result is luck-dependent.

**The mechanism here is the refusal policy.** A question whose metric scores land near `metric_score_margin` can fall either side of it across samples, which is why a flip shows up as answered-versus-asked rather than as a different number.

**What each flip costs the published figures.** The rate a flip moves depends on what the question was supposed to do, and the denominators are the full eval set's, so these are the swings on `RESULTS.md`:

- `t2-05` (should answer): moves **over-refusal** and **execution accuracy**, denominator 55 answerable questions, so ±1.8pp on each depending which sample you draw.

This is the honest cost of an n=1 headline: those figures are not wrong, but they are one draw, and a reader should read them with this swing attached.

## `baseline` — 2 samples over 80 questions

From `benchmark/runs/variance-baseline-r2/`. Same provider, same config hash, temperature 0.

**Coverage: all 80 questions.** Not a subset, so this is representative of the arm rather than sensitive to a chosen slice.

### Did anything change?

**4 of 80 questions changed outcome between runs.**

| Question | run 0 | run 1 |
|---|---|---|
| `am-18` | answered, value=None | asked, value=None |
| `am-25` | asked, value=None | answered, value=None |
| `t2-11` | answered, value=True | answered, value=False |
| `t3-04` | answered, value=True | answered, value=False |

A flip at temperature 0 is not a contradiction: the provider does not guarantee determinism. Each one above is a question whose published result is luck-dependent.

**The mechanism here is free-form generation, not a refusal policy** — the baseline has none, only its own option to decline. Its flips therefore come in two kinds, and the second is the more serious: a *behaviour* flip, where it declines on one sample and answers on the other, and a *value* flip, where it answers both times and computes a different number. A value flip means the SQL itself changed between identical requests.

**What each flip costs the published figures.** The rate a flip moves depends on what the question was supposed to do, and the denominators are the full eval set's, so these are the swings on `RESULTS.md`:

- `am-18` (should refuse): moves **under-refusal** and **behaviour accuracy**, denominator 25 should-not-answer questions, so ±4.0pp on each depending which sample you draw.
- `am-25` (should refuse): moves **under-refusal** and **behaviour accuracy**, denominator 25 should-not-answer questions, so ±4.0pp on each depending which sample you draw.
- `t2-11` (should answer): moves **over-refusal** and **execution accuracy**, denominator 55 answerable questions, so ±1.8pp on each depending which sample you draw.
- `t3-04` (should answer): moves **over-refusal** and **execution accuracy**, denominator 55 answerable questions, so ±1.8pp on each depending which sample you draw.

This is the honest cost of an n=1 headline: those figures are not wrong, but they are one draw, and a reader should read them with this swing attached.

## What would make this stronger

- **More samples.** Two runs detect a coin-flip question but not a rare one, and the cost is linear in free-tier days.
- **Full coverage for every arm.** Where an arm above is scoped to the subset, the remaining questions are unmeasured, and the subset was chosen to be sensitive rather than representative.
- **A third provider.** Everything here is one model on one provider, so it measures run-to-run stability, not robustness to the model changing underneath.
